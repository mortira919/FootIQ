# Amplua API: контракт между клиентом и сервером

Здесь описано, что Flutter-клиент Amplua отправляет серверу и что ждёт в ответ. Клиент уже написан под этот контракт: достаточно поднять сервер и запустить приложение с `--dart-define=API_URL=https://…`, экраны менять не придётся.

**Где это в коде клиента:**

| Файл | Что там |
| --- | --- |
| `lib/data/backend.dart` | Контракт в виде Dart-интерфейса: по методу на эндпоинт |
| `lib/data/remote_backend.dart` | HTTP-реализация по этому документу: заголовки, токены, refresh, ошибки |
| `lib/data/local_backend.dart` | «Сервер на устройстве» с теми же правилами. Работает, пока `API_URL` не задан. **Эталон бизнес-логики:** лимиты, серия, блокировка смены роли, лиги считаются там так, как должен считать сервер |
| `lib/data/auth.dart` | Нативные окна Google и Apple, которые отдают токен для `/auth/{provider}` |
| `test/remote_backend_test.dart` | JSON-примеры из этого документа. Если сервер отвечает так же, клиент их разберёт: тест это проверяет |

Имена полей можно менять по договорённости, но тогда вместе с `remote_backend.dart`, `models.dart` и тестом.

## Общие правила

- **Формат:** REST + JSON, UTF-8, ключи в camelCase. Префикс версии `/v1`.
- **Авторизация:** `Authorization: Bearer <accessToken>` на всех запросах, кроме `/auth/*`.
  - На 401 клиент один раз вызывает `POST /v1/auth/refresh` и повторяет запрос.
  - Если refresh тоже вернул ошибку, клиент стирает токены и отправляет игрока на экран входа.
  - Токены лежат в Keychain / Keystore (`flutter_secure_storage`).
- **Часовой пояс:** каждый запрос несёт `X-Timezone-Offset: 180` (минуты от UTC, как `DateTime.now().timeZoneOffset`). «Сегодня» для задачи дня, серии и дневных лимитов считается по дню игрока с этим смещением.
- **Даты:** ISO 8601 в UTC (`2026-09-28T09:12:00Z`).
- **Enum'ы** передаются строками, как имена в коде: `polygon`, `gk`, `gold`. Полный список в «Моделях данных».
- **Ошибки:** HTTP-код и тело `{"error": {"code": "limit_reached", "message": "Текст для игрока"}}`.
  - `message` клиент показывает как есть, поэтому он по-русски и человеческий.
  - Дополнительные поля кладутся рядом с `code` (например, `"daysLeft": 12`) и доходят до клиента в `ApiException.data`.
  - Коды, по которым клиент ветвится: `unauthorized`, `limit_reached`, `pro_required`, `position_locked`, `league_not_found`, `league_name_taken`, `not_league_owner`, `validation_error`, `ai_consent_required`. На любой другой код показывается `message`.
  - `ai_consent_required` (403): нет согласия на передачу ответа ИИ-сервису. Приходит на `POST /v1/modes/video/start` и `POST /v1/attempts/video`. Клиент показывает шит согласия и после «Согласен» шлёт `PATCH /v1/me {aiConsent: true}`. Попытка при этом не списывается.
  - `account_banned` (403): аккаунт забанен модератором. Клиенту достаточно показать `message` (в нём контакт поддержки). Доступно только `DELETE /v1/me`.
- **Таймауты клиента:** 20 с на запрос, 30 с на `POST /attempts/video` (там LLM). При таймауте игрок может повторить, поэтому отправка попыток должна быть идемпотентной по `sessionId`.
- **Стенд и прод разделены.** Прод: отдельное приложение Fly `amplua-api` со своей базой, адрес **`https://amplua.app`**: на нём и API (`/v1`), и сайт со страницами `/privacy`, `/terms`, `/delete-account`, `/l/<код>`, на которые ведут ссылки в приложении. Один сервер, один TLS-сертификат Fly, машина не засыпает. Технический адрес того же сервера `https://amplua-api.fly.dev`, в приложение его не вшивать. Стенд: `https://footiq.fly.dev`, на нём есть dev-вход по имени и `/stand`. На проде (`AMPLUA_ENV=prod`) пути стенда (`/stand`, `/auth/dev-login`, старые пути без `/v1`, `/docs`) отвечают 404.
- **HEAD** на любой GET-путь ведёт себя как GET без тела: `curl -sI https://<прод>/v1/me` без токена отвечает 401.
- **Безопасность профиля и токенов (Apple 1.6):** только HTTPS. Access-токен живёт 1 час, refresh-токен 30 дней и одноразовый: каждый `refresh` выдаёт новую пару, новый вход сбрасывает сессии на других устройствах. Вход только через Google или Apple с проверкой подписи провайдера. Ограничение частоты: 20 входов в минуту с IP, 60 запросов в минуту на игрока.
- **Правило доверия:** всё, что влияет на рейтинг (ELO, серия, лимиты, PRO, исход задачи), считает и хранит сервер. Клиент отправляет только сырые действия игрока.

## Вход и аккаунт

Вход только через Google или Apple (Apple показывается на iOS). Анонимного входа нет. Один игрок = одна пара `provider + sub` из токена провайдера.

| Метод и путь | Клиент отправляет | Сервер отдаёт |
| --- | --- | --- |
| `POST /v1/auth/google` | `{idToken}` | `{accessToken, refreshToken, user: Me}` |
| `POST /v1/auth/apple` | `{identityToken, authorizationCode, givenName, familyName}` (имя может быть `null`) | `{accessToken, refreshToken, user: Me}` |
| `POST /v1/auth/refresh` | `{refreshToken}` | `{accessToken, refreshToken}`; на невалидный токен 401 |
| `POST /v1/auth/logout` | `{refreshToken}` | `204`: refresh-токен отзывается. Клиент стирает токены, даже если запрос упал |
| `DELETE /v1/me` | — | `204`. Обязательно для App Store (5.1.1(v)) и Google Play |

Что проверяет сервер при входе:

- **Google:** подпись `idToken` по ключам Google, `aud` = web/server client ID (тот, что клиент получает в `GOOGLE_SERVER_CLIENT_ID`), `iss` = `accounts.google.com`, срок жизни. Email берётся из токена.
- **Apple:** подпись `identityToken` по JWKS Apple, `aud` = bundle id приложения (`com.amplua.amplua`), `iss` = `https://appleid.apple.com`. **Имя Apple отдаёт только при самом первом входе,** поэтому клиент шлёт `givenName` и `familyName` сразу, а сервер сохраняет их, если имя ещё не задано.
  - `authorizationCode` сервер обменивает на refresh-токен Apple (`POST https://appleid.apple.com/auth/token`, `grant_type=authorization_code`) и хранит его: им отзывается вход при удалении аккаунта. Новый код при повторном входе заменяет старый токен.
  - `client_secret` для обмена и отзыва: JWT ES256, подписанный ключом Sign in with Apple (`.p8`): `iss` = Team ID, `sub` = bundle id, `aud` = `https://appleid.apple.com`, `kid` = Key ID. Ключи в секретах сервера: `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`.
  - Email из токена Apple принимается любой, без белого списка доменов: и `…@privaterelay.appleid.com`, и `…@private.icloud.com` (новые relay-адреса Apple с 24.08.2026), и обычный. Apple присылает email только при первом входе, повторный вход без email сохранённый адрес не стирает.
- Первый вход создаёт игрока со стартовым ELO 800 и `position: null`. Клиент после входа смотрит на `user.position`: `null` ведёт в выбор амплуа, иначе сразу в приложение (новое устройство получает весь прогресс).

`DELETE /v1/me` → `204`. Удаление сразу и необратимо, одной транзакцией:

- **Что удаляется:** профиль (id, email, имя, амплуа, регион, часовой пояс, согласие на ИИ), все попытки, в том числе ответы в Раздевалке и разборы тренера, ELO и серия, сессии и refresh-токены, членство в чужих лигах, записи семантического кэша и журнал запросов к LLM, жалобы и блокировки, которые создал игрок, а также жалобы и блокировки, где он цель.
- **Лиги, где игрок создатель,** удаляются у всех участников вместе с таблицей: код перестаёт работать, `GET /v1/leagues` у участников их больше не возвращает.
- **Apple:** сервер отзывает сохранённый refresh-токен через `POST https://appleid.apple.com/auth/revoke` (`token_type_hint=refresh_token`).
- **RevenueCat:** сервер удаляет подписчика `DELETE https://api.revenuecat.com/v1/subscribers/{Me.id}` (секретный ключ `REVENUECAT_SECRET_KEY`; по документации удаление ставится в очередь асинхронно).
- **Сбой Apple или RevenueCat удаление не останавливает:** данные в базе стираются в любом случае, ошибка пишется в журнал сервера.
- **После удаления** старый `accessToken` и `refreshToken` дают 401. Повторный вход тем же Google или Apple создаёт нового игрока с ELO 800 и `position: null`.
- **Подписку не отменяет:** она принадлежит аккаунту App Store / Google Play, клиент предупреждает об этом и даёт ссылку на управление подпиской. После нового входа «Восстановить покупки» возвращает PRO: RevenueCat при `Restore Behavior = Transfer to new App User ID` (значение по умолчанию в проекте RevenueCat) переносит чек на новый `app_user_id`. Эту настройку в проекте RevenueCat не менять на «Keep with original App User ID».
- **Что хранится после удаления:** ежедневные снапшоты диска сервера до 5 дней, журналы запросов хостинга до 30 дней, записи о покупках у Apple, Google и RevenueCat по их правилам. То же написано в политике конфиденциальности.

### Вход для ревьюеров

Ревьюер App Store и Google Play входит по логину и паролю в один служебный аккаунт с прогрессом и лигами. В приложении вход открывается скрытой дверью на экране входа (долгое нажатие на логотип). Логин, пароль и подсказку «долго нажмите на логотип» команда вписывает в App Store Connect (App Review Information, Notes) и в Play Console (App access).

| Метод и путь | Клиент отправляет | Сервер отдаёт |
| --- | --- | --- |
| `POST /v1/auth/review` | `{login, password}` | `{accessToken, refreshToken, user: Me}`, как `/auth/google`. Неверный логин или пароль: 401 `unauthorized` с `message` «Неверный логин или пароль». Больше 5 попыток в минуту с одного IP: 429. Вход выключен на сервере: 404 `not_found` на любой запрос |

```json
{"login": "review@amplua.app", "password": "…"}
```

- **Включение на сервере:** `REVIEW_LOGIN_ENABLED=true`, `REVIEW_LOGIN`, `REVIEW_PASSWORD_HASH`. Убрали любой из них, и вход пропал. В секретах только хэш пароля (PBKDF2-SHA256), его печатает `python scripts/review_password.py`.
- **Аккаунт** отвязан от Gmail: в `Me` у него `provider: "google"`, `email: "review@amplua.app"`, но войти в него через Google нельзя.
- **Наполнение:** `python scripts/seed_reviewer.py --password-login` на сервере (`flyctl ssh console -a <приложение> -C "…"`):
  - амплуа «опорный» (у него есть видеоразборы), около 20 попыток во всех трёх режимах, ELO и история за неделю, серия задач дня 5 дней;
  - 2 лиги по 5 участников: ревьюер создатель, 4 служебных игрока в каждой. Служебные игроки видны только в этих лигах;
  - флаги: `--pro` выдаёт PRO на год, `--consent` ставит согласие на ИИ (по умолчанию нет, чтобы ревьюер увидел экран согласия).

  С `--email <gmail>` скрипт берёт прежний аккаунт ревьюера на Gmail и отвязывает его. Повторный запуск наполняет заново.
- **Удаление:** если ревьюер проверит удаление аккаунта, данные сотрутся по-настоящему. Следующий вход откроет пустой аккаунт (ELO 800). Прогресс возвращает повторный запуск скрипта, поэтому после каждого ревью его стоит перезапускать.
- **Запасной вариант без пароля:** `seed_reviewer.py --email <тестовая Google-учётка>` наполняет обычный Google-аккаунт. Заготовка привязывается к учётке при первом входе с подтверждённым email.

### Удаление через веб

Публичная страница для ссылки в форме Data safety Google Play: удалить аккаунт можно, даже если приложения на телефоне уже нет. Клиенту эти пути не нужны, это HTML для браузера.

| Метод и путь | Что отправляют | Что отдаёт сервер |
| --- | --- | --- |
| `GET /delete-account` | — | HTML: форма с email, что удаляется и что остаётся, срок, путь удаления в приложении |
| `POST /delete-account` | форма `email=…` (`application/x-www-form-urlencoded`) | HTML «Проверь почту». Ответ одинаковый для знакомого и незнакомого адреса. Письмо уходит, только если адрес принадлежит аккаунту (без учёта регистра). Кривой адрес 400, больше 5 запросов в минуту с IP или 2 на адрес: 429 |
| `GET /delete-account/confirm?token=…` | — | HTML с кнопкой «Удалить навсегда». Ссылка сама ничего не удаляет, чтобы превью ссылок в почтовиках не стирало аккаунты. Устаревшая или использованная ссылка: 410 |
| `POST /delete-account/confirm` | форма `token=…` | Удаление, такое же, как `DELETE /v1/me` (Apple revoke, RevenueCat, все данные), и HTML «Аккаунт удалён». Устаревшая или использованная ссылка: 410 |
| `GET /delete` | — | `308` на `/delete-account` (старый адрес) |

- **Ссылка:** токен из 32 случайных байт, в базе хранится только его SHA-256. Живёт 24 часа, одноразовая (запрос удаляется вместе с аккаунтом).
- **Письмо:** SMTP из секретов сервера (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`), ссылка строится от `PUBLIC_URL`. Письмо отправляется в фоне, поэтому время ответа не выдаёт, есть ли аккаунт.
- **Apple со скрытым адресом:** игрок вводит relay-адрес, письмо приходит на настоящую почту через переадресацию Apple.
- **Для Data safety:** URL `https://<домен>/delete-account`.

## Профиль и прогресс

Главная и Профиль строятся из одного ответа `GET /v1/me`: при запуске это один запрос. Клиент перезапрашивает `me` при возврате приложения из фона и в полночь.

| Метод и путь | Клиент отправляет | Сервер отдаёт |
| --- | --- | --- |
| `GET /v1/me` | — | `Me` |
| `PATCH /v1/me` | Любое из `{name, position, region, coach, aiConsent}` | `Me` |
| `GET /v1/me/attempts?limit=30&before=<ISO>` | — | `{items: [Attempt], nextBefore: ISO \| null}`, новые сверху |

Объект `Me`:

```json
{
  "id": "u_8f2k",
  "name": "Игрок 4821",
  "email": "player@gmail.com",
  "provider": "google",
  "position": "cm",
  "positionLockDays": 12,
  "region": "Россия",
  "coach": "base",
  "isPro": false,
  "elo": 912,
  "positionElo": {"cm": 874, "am": 838},
  "eloHistory": [800, 814, 820, 812, 824, 826, 830, 912],
  "radar": [0.8, 0.5, null, 0.62, 0.7],
  "streak": 4,
  "streakWeek": [false, false, false, true, true, true, true],
  "dailyDone": true,
  "daily": {"sceneId": "cm", "mirrored": false},
  "rushBest": 9,
  "attemptsLeft": {"polygon": null, "rush": 2, "video": 1},
  "sessionsCount": 37,
  "aiConsentAt": "2026-10-06T12:30:00Z"
}
```

| Поле | Что значит | Как считать (эталон в `local_backend.dart`) |
| --- | --- | --- |
| `name` | Имя в Профиле и рейтингах | Пока не задано, выдать что-то вроде `Игрок 4821` |
| `email`, `provider` | Чем вошёл игрок (`google`, `apple`) | Из токена провайдера. Показывается в Профиле |
| `position` | Текущее амплуа, `null` до онбординга | |
| `positionLockDays` | Дней до следующей смены роли, `null` если можно сейчас | 30 дней от последней смены, у PRO всегда `null` |
| `coach` | Персона тренера | Если PRO истёк, отдавать `base` |
| `elo` | Общий Tactical ELO | 800 + сумма `eloDelta` всех попыток |
| `positionElo` | ELO по ролям, где были попытки | 800 + сумма `eloDelta` по роли. Роли без попыток можно не отдавать, клиент подставит 800 |
| `eloHistory` | 8 значений ELO на конец дня: 7 дней назад … сегодня | `[0]` = ELO до начала окна |
| `radar` | 5 значений 0..1 для текущей роли | Среднее качество попыток по оси. **`null` = по оси ещё не было попыток**, `0` = были, но все с ошибкой |
| `streak`, `streakWeek` | Серия задач дня и 7 флагов (старый день … сегодня) | Серия жива, если последняя задача дня была сегодня или вчера. Любой исход, даже ошибка, продлевает серию |
| `dailyDone` | Задача дня сегодня уже решена | |
| `daily` | Задача дня для роли игрока: одна на весь день | Сцена по `{sceneId, mirrored}`, см. «Задачи 2D». Отдельный `GET /puzzles/daily` не нужен |
| `rushBest` | Рекорд: больше всего решённых задач за один Rush | |
| `attemptsLeft` | Остаток попыток на сегодня, `null` = без лимита | Free: Rush 2, Видео 1, Полигон без лимита. PRO: всё `null` |
| `sessionsCount` | Сколько всего попыток | Счётчик в шапке Профиля |
| `aiConsentAt` | Когда игрок согласился передавать ответы ИИ-сервису, `null` = согласия нет | `PATCH /v1/me {aiConsent: true}` ставит время первого согласия (повторное «да» его не меняет), `{aiConsent: false}` отзывает и обнуляет |

Ранг («Новичок» … «UEFA Pro») клиент считает сам по `elo`.

Правила `PATCH /v1/me`:

- **Первый выбор позиции** (когда `position` ещё `null`) не запускает блокировку.
- **Смена позиции на Free** не чаще раза в 30 дней, иначе 403 `position_locked` с `daysLeft` рядом с кодом. На PRO ограничения нет. Клиент перед сменой сам предупреждает о 30 днях, но решает сервер.
- **ELO по позициям** хранится отдельно и при смене роли не теряется.
- **Тренеры** `pep`, `jose`, `jurgen` доступны только на PRO, иначе 403 `pro_required`.
- **Имя:** 2–20 символов после обрезки пробелов, иначе 400 `validation_error`.
- **Фильтр мата и оскорблений** для имени: 400 `validation_error` с `message` «В имени есть недопустимые слова. Выбери другое». Фильтр ловит латиницу и цифры вместо кириллицы (`xyй`, `6ля`), пробелы, точки и дефисы между буквами (`х у й`, `х.у.й`), повтор букв (`хуууй`) и транслит (`blyad`). Имя из Apple при первом входе проходит тот же фильтр: если не прошло, игрок получает имя по умолчанию.

## Старт режима с лимитом

`POST /v1/modes/{rush|video}/start` → `{"sessionId": "s_91x", "attemptsLeft": 1}` или 403 `limit_reached`.

- Попытка списывается на старте, а не в конце, чтобы нельзя было выйти и переиграть.
- `sessionId` клиент передаёт при отправке результата: одна сессия даёт один результат. Повторная отправка с тем же `sessionId` возвращает тот же ответ, без второго списания и второго начисления ELO.
- Для видео клиент шлёт `{puzzleId}` и вызывает `start` не при открытии экрана, а на первом стоп-кадре, когда видны варианты A/B/C. Закрыть экран раньше бесплатно (например, если видео не загрузилось).

## Задачи 2D: Полигон, задача дня, Rush

Клиент отправляет только точку, куда игрок дал пас или открылся. Исход и ELO считает сервер: ему нужны те же сцены и порт `evaluate()` из `lib/engine/tactics.dart` (около 40 строк геометрии: офсайд, конус отбора, тень опеки, золотая зона). Проверочные случаи для порта: `test/polygon_test.dart`.

**Сцены** зашиты в `lib/engine/scenes.dart`: 10 штук, по одной на роль, `id` совпадает с кодом роли (`gk`, `cb`, …, `ss`). Каждую можно зеркалить по флангу, поэтому сцена определяется парой `{sceneId, mirrored}`. Координаты в метрах: поле 68 × 105, `x` слева направо, `y` от чужих ворот к своим.

| Метод и путь | Клиент отправляет | Клиент читает из ответа |
| --- | --- | --- |
| `POST /v1/attempts/polygon` | `{sceneId, mirrored, target: {x, y} \| null, daily}`; `null` = вышли 7 секунд | `{reason, eloDelta, attempt, me}` |
| `POST /v1/attempts/rush` | `{sessionId, answers: [{sceneId, mirrored, target \| null}]}` | `{eloDelta, attempt, me}` |

Что сервер делает с попыткой:

1. Прогоняет `target` через `evaluate()` и получает `reason`: `optimal` даёт `gold`, `safe` даёт `silver`, остальные причины дают `error`.
2. Считает `eloDelta` от ELO игрока **на этой позиции** (`positionElo`), сложности сцены (1..5) и качества (gold 1, silver 0.5, error 0). В клиенте стоит простой Elo `eloDelta()`, по ТЗ нужен Glicko-2.
3. Если `daily: true`:
   - сцена должна совпадать с `Me.daily`, иначе `validation_error`;
   - если задача дня сегодня ещё не засчитана, `streak` растёт.
4. Сохраняет `Attempt` и возвращает свежий `me`: клиент не перезапрашивает `GET /v1/me`.

Анимацию (кто перехватил мяч, куда он долетел) клиент рисует по своей копии `evaluate()`, а исход и ELO берёт из ответа.

**Rush.** Спринт на 3 минуты, 3 жизни. Все ответы уходят одним запросом в конце, рейтинг обновляется один раз за спринт. Сейчас считается так:

- `score` = среднее качество ответов, `difficulty` = средняя сложность сцен.
- `solved` = число ответов без `error`, оно же обновляет `rushBest`. Заголовок попытки: `Серия {solved} из {total}`.
- `outcome` спринта: `gold` при score ≥ 0.75, `silver` при ≥ 0.4, иначе `error`.
- Спринт, прерванный до первого ответа, клиент не отправляет вовсе.
- Защита от подделки: отклонять ответы после третьей ошибки и отправку позже ~3,5 минуты после `start`.

## Видео-разбор и AI-тренер

Игрок смотрит эпизод, выбирает один из вариантов A/B/C и пишет объяснение. Сервер оценивает ответ по шкале 1..10 через LLM. Правильный вариант и ключевые факторы до ответа на клиент не отдаются.

**Согласие (Apple 5.1.2(i), Google User Data).** Без `Me.aiConsentAt` оба эндпоинта ниже отвечают 403 `ai_consent_required`, попытка не списывается. Если согласие отозвали между `start` и отправкой ответа, сервер возвращает попытку (сессия отменяется) и тоже отвечает 403.

| Метод и путь | Клиент отправляет | Сервер отдаёт |
| --- | --- | --- |
| `GET /v1/puzzles/video` | — | `VideoPuzzle` для роли игрока. Попытку не списывает |
| `POST /v1/modes/video/start` | `{puzzleId}` | `{sessionId, attemptsLeft}` или 403 `limit_reached` |
| `POST /v1/attempts/video` | `{sessionId, puzzleId, choice: 0..2, answer}` | `{score, eloDelta, review, correct, attempt, me}` |

`correct` (0..2) приходит только в ответе на попытку: по нему клиент подсвечивает правильный вариант на кадре.

`VideoPuzzle`:

```json
{
  "id": "v_gk_01",
  "position": "gk",
  "sceneId": "gk",
  "title": "Выход из-под давления",
  "videoUrl": "https://cdn.example/gk_01.mp4",
  "options": [{"x": 18, "y": 96}, {"x": 52, "y": 91.5}, {"x": 34, "y": 87}],
  "chips": ["Дуга прессинга", "Тень опеки", "Пас на ход"]
}
```

- `sceneId` указывает на 2D-сцену, из которой отрендерен клип. По ней клиент ставит метку «ТЫ» и точки A/B/C на кадре.
- Если `videoUrl` нет, клиент играет встроенный клип `assets/videos/<роль>.mp4`.

`Review`, карточка разбора тренера:

```json
{
  "choice": "B",
  "answer": "текст игрока",
  "checklist": [
    {"ok": true, "text": "Вариант B верный"},
    {"ok": false, "text": "Не названо: тень опеки"}
  ],
  "coach": "pep",
  "reply": "Реплика тренера в его стиле"
}
```

- **Рубрика (итог 1..10):** верный вариант до 3 баллов, зона ответственности роли до 3, названные факторы пространства до 2, причинно-следственная логика до 2. Её же получает LLM в системном промпте.
- **Что уходит в LLM:** только текст ответа, амплуа (словами, например «опорный полузащитник») и задача: название эпизода, эталонный разбор, варианты, верный и выбранный вариант, ключевые факторы, стиль тренера. Ни email, ни имени, ни id игрока, ни других его данных. В системном промпте правила безопасности: только тактика эпизода, без оскорблений и советов вне футбола, текст игрока это данные, а не инструкции.
- **Фильтр выдачи:** `reply` и каждый пункт `checklist` проходят фильтр мата, оскорблений и опасных тем (самоповреждение, насилие, наркотики, оружие). Не прошёл, LLM не ответила за 20 секунд или вернула не тот формат: сервер оценивает запасной рубрикой на ключевых словах (порт `grade()` из `lib/data/video.dart`, `app/video.py` на сервере). Игрок в любом случае получает разбор.
- **Семантический кэш** общий для всех игроков: ключ = эпизод + амплуа + тренер + выбранный вариант + текст ответа без регистра, пунктуации и лишних пробелов. Из кэша берутся только `score`, `checklist` и `reply`. `Review.answer` всегда текст текущего игрока, сам текст в кэше не хранится.
- **Журнал запросов к LLM** (`llm_log`): время, игрок, попытка, провайдер, длительность и статус (`ok`, `cache`, `filtered`, `error`). Текст ответа в журнал не пишется. Журнал удаляется вместе с аккаунтом.
- **Жалоба на разбор:** `POST /v1/reports {targetType: "review", targetId: Attempt.id, reason}` (см. «Жалобы и блокировки»). Только на свою попытку, на чужую 404 `not_found`.
- **Провайдер** задаётся на сервере (`LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY`). Сейчас поддержан `anthropic` (Claude, по умолчанию `claude-haiku-4-5`). Пока провайдер не выбран, работает только запасная рубрика (см. «Открытые вопросы к бэкенду»).
- **Тренер** берётся из `Me.coach`, клиент его не передаёт. У `reply` три тона по итогу: ≥ 8, 5..7, ≤ 4.
- **ELO:** качество = `score / 10`, ось радара 4 («Обоснования»).

`Leaderboard`:

```json
{
  "players": [
    {"id": "u_1", "rank": 1, "name": "Артём", "position": "cm", "elo": 1720, "region": "Россия", "delta": 12, "isMe": false}
  ],
  "me": {"id": "u_8f2k", "rank": 348, "name": "Игрок 4821", "position": "cm", "elo": 912, "region": "Россия", "delta": 4, "isMe": true},
  "total": 12840
}
```

- `players` отсортированы по `rank`. Отдавать топ-100 и соседей игрока (по 2 выше и ниже `me`). Между ними ранги могут прерываться: клиент ставит разделитель «···».
- `me` приходит всегда. Клиент показывает место `me.rank` из `total` и сколько ELO не хватает до ближайшего порога (топ-100/10/3/1). Для этого игрок на пороговом месте должен быть в `players`.
- `delta` = последнее изменение ELO игрока (стрелка вверх или вниз).
- Передача прав в лиге выбирает участника из таблицы лиги по `id`, поэтому `id` у игроков в `players` обязателен.

`League`:

```json
{"id": "l_91x", "name": "Пятничный футбол", "code": "PT7K2Q", "membersCount": 6, "myRank": 4, "owner": {"id": "u_1", "name": "Артём"}}
```

- `membersCount` включает самого игрока. `owner.id` клиент сравнивает с `Me.id`: создателю доступны переименование, передача и удаление, участнику выход.
- Код лиги: 6 символов из `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (без похожих 0/O и 1/I). Клиент приводит ввод к верхнему регистру и не даёт ввести символы вне алфавита. Сервер генерирует только коды, которых ещё нет.
- Название лиги: 1–32 символа, уникально среди лиг одного игрока без учёта регистра. Тот же фильтр мата, что для имени: 400 `validation_error` «В названии лиги есть недопустимые слова. Выбери другое» на `POST /v1/leagues` и `PATCH /v1/leagues/{id}`.
- **Заблокированные игроки** (см. «Жалобы и блокировки») не приходят в `players` у того, кто заблокировал, во всех трёх таблицах. Ранги остальных не сдвигаются, поэтому между соседними строками может появиться пропуск. У самого заблокированного таблицы не меняются.
- **Забаненные модератором** игроки не попадают ни в одну таблицу.
- Регионы зашиты в клиенте: Россия, Казахстан, Беларусь, Узбекистан, Армения, Грузия.

Механизмы, которые требуют Apple 1.2 и Google UGC / AI-Generated Content: пожаловаться на игрока, лигу или ответ ИИ-тренера и заблокировать игрока.

| Метод и путь | Клиент отправляет | Сервер отдаёт |
| --- | --- | --- |
| `POST /v1/reports` | `{targetType: "user" \| "league" \| "review", targetId, reason, comment?}` | `204`. Цели нет: 404 `not_found`. Кривой `targetType` или `reason`, жалоба на себя: 400 `validation_error` |
| `POST /v1/blocks` | `{userId}` | `204`. Повторная блокировка ничего не меняет. Игрока нет: 404 `not_found`. Себя: 400 `validation_error` |

```json
{"targetType": "user", "targetId": "u_1", "reason": "offensive_name", "comment": "Мат в имени"}
```

Ответ `GET /v1/blocks`:

```json
[{"id": "u_1", "name": "Артём", "position": "cm"}]
```

- **`comment`:** до 500 символов, необязательно.
- **Дубли:** повторная жалоба того же игрока на ту же цель, пока первая не разобрана, новой записи не создаёт. Ответ тот же `204`, чтобы клиент не ветвился.
- **Что видит модератор:** снимок контента на момент жалобы (имя, название лиги, реплику тренера) и текущее состояние цели.
- **Блокировка** скрывает игрока из моих таблиц: глобальной, региональной и таблиц лиг.

## Подписка PRO

Покупку и восстановление будет делать RevenueCat SDK на клиенте, эндпоинтов покупки на сервере не нужно. Серверу нужно знать, есть ли у игрока PRO, чтобы применять лимиты.

| Метод и путь | Кто шлёт | Что отдаёт сервер |
| --- | --- | --- |
| `POST /v1/webhooks/revenuecat` | RevenueCat, с заголовком `Authorization` из дашборда | `200 {"ok": true, "duplicate": false}`; повтор события `200 {"ok": true, "duplicate": true}`; неверный или пустой секрет 401 `unauthorized` |
| `POST /v1/me/sync-subscription` | Клиент после покупки и на «Восстановить покупки» | `Me` со свежим `isPro` |

Тело вебхука (формат RevenueCat):

```json
{
  "api_version": "1.0",
  "event": {
    "id": "CD489E0E-5D02-4C4E-A6A9-3D4A4C5F2A1B",
    "type": "RENEWAL",
    "app_user_id": "u_8f2k",
    "original_app_user_id": "u_8f2k",
    "aliases": ["u_8f2k"],
    "entitlement_ids": ["pro"],
    "expiration_at_ms": 1791100000000,
    "environment": "PRODUCTION"
  }
}
```

- **Секрет:** значение заголовка `Authorization` задаётся в дашборде RevenueCat и на сервере в `REVENUECAT_WEBHOOK_SECRET`. Принимается и `Bearer <секрет>`, и сам секрет.
- **Идемпотентность:** обработанные `event.id` хранятся. RevenueCat при ошибке повторяет событие с тем же `id` до 5 раз, повтор состояние не меняет.
- **Игрок:** `app_user_id` = `Me.id` (клиент логинится в RevenueCat SDK с этим id). Ищем по `app_user_id`, `original_app_user_id` и `aliases`. Незнакомого игрока событие не трогает, ответ всё равно 200.
- **Как события меняют `isPro`** (названия по документации RevenueCat, Event Types and Fields):

| Событие | Что делает сервер |
| --- | --- |
| `INITIAL_PURCHASE`, `RENEWAL`, `UNCANCELLATION`, `PRODUCT_CHANGE`, `SUBSCRIPTION_EXTENDED`, `TEMPORARY_ENTITLEMENT_GRANT`, `REFUND_REVERSED`, `NON_RENEWING_PURCHASE` | PRO до `expiration_at_ms`; без даты бессрочно |
| `CANCELLATION` | Отмена продления: PRO остаётся до конца оплаченного периода (`expiration_at_ms`). С `cancel_reason = CUSTOMER_SUPPORT` это возврат денег: PRO снимается сразу |
| `EXPIRATION` | PRO снимается |
| `BILLING_ISSUE` | С `grace_period_expiration_at_ms` доступ сохраняется до конца grace period; без него ничего не меняется до `EXPIRATION` |
| `TRANSFER` | Покупка переехала на другой аккаунт: у `transferred_from` PRO снимается, `transferred_to` получает его срок |
| `SUBSCRIPTION_PAUSED`, `TEST`, `INVOICE_ISSUANCE` и прочие | Ничего не меняют |

- **Сверка с REST API:** после каждого нового события и в `sync-subscription` сервер спрашивает `GET https://api.revenuecat.com/v1/subscribers/{Me.id}` (секретный ключ `REVENUECAT_SECRET_KEY`, так советует RevenueCat). PRO активен, если entitlement `pro` (имя в `REVENUECAT_ENTITLEMENT`) не истёк или идёт grace period (`grace_period_expires_date`). Если RevenueCat не ответил, статус не меняется.
- **Что даёт PRO:** безлимитные Rush и Видео, тренеры Пеп, Жозе и Юрген, смену роли без 30-дневного ожидания.
- **Когда PRO истёк или деньги вернули:** роль сохраняется, тренер возвращается к `base`, снова действуют лимиты Free.

**Статус на клиенте:** RevenueCat SDK ещё не подключён. Кнопки «Оформить» и «Восстановить» работают на моке магазина и затем вызывают `sync-subscription`. Пока SDK и ключей RevenueCat нет, PRO на стенде включается вручную полями `subscription_tier` и `pro_until` в базе.

## Как подключить клиент к серверу

1. **Сборка с сервером:** для релиза в сторы только `API_URL=https://amplua.app`. Адрес вшивается в приложение: если выпустить сборку с `*.fly.dev` и потом переехать, у всех установивших она перестанет работать. Для тестов стенд `https://footiq.fly.dev`.
   ```
   flutter run --dart-define=API_URL=https://amplua.app \
               --dart-define=GOOGLE_SERVER_CLIENT_ID=<web client id>.apps.googleusercontent.com \
               --dart-define=GOOGLE_IOS_CLIENT_ID=<ios client id>.apps.googleusercontent.com
   ```
   Без `API_URL` приложение работает на `LocalBackend`, а вход фейковый (без окон Google и Apple). На Android-эмуляторе локальный сервер доступен как `http://10.0.2.2:<порт>`.
2. **Google Cloud Console** (один проект, три OAuth-клиента):
   - Web client: его ID идёт в `GOOGLE_SERVER_CLIENT_ID` и в проверку `aud` на сервере.
   - Android client: пакет `com.amplua.amplua` и SHA-1 ключа подписи (debug: `keytool -list -v -keystore ~/.android/debug.keystore`, release: из Play Console).
   - iOS client: bundle id приложения. Его ID идёт в `GOOGLE_IOS_CLIENT_ID`, а «reversed client ID» нужно добавить в `ios/Runner/Info.plist` как URL scheme (`CFBundleURLTypes`).
3. **Apple:**
   - в Xcode для Runner включить capability «Sign in with Apple»;
   - в Apple Developer включить её для App ID;
   - сервер проверяет `aud` = bundle id.
4. **Проверка контракта без приложения:** `flutter test test/remote_backend_test.dart`. JSON в тесте совпадает с примерами выше: если сервер отвечает так же, клиент его разберёт.

## Открытые вопросы к бэкенду

- [ ] Сцены 2D: держим копию на сервере и в приложении или сервер отдаёт их сам (`GET /v1/puzzles/scenes`)? На каком языке будет порт `evaluate()`?
- [ ] Формула рейтинга: оставляем простой Elo из клиента или сразу Glicko-2 по ТЗ (§4.3)?
- [ ] **LLM-провайдер и договор о данных.** Какая LLM оценивает видео-ответы и кто пишет промпты тренеров? По ТЗ кандидаты GPT-4o-mini или Claude Haiku. Сервер готов к Claude (`LLM_PROVIDER=anthropic`), до решения работает запасная рубрика. Нужно до релиза:
  - договор (DPA) или условия провайдера, где прямо сказано, что данные API не используются для обучения моделей;
  - срок хранения запросов у провайдера и есть ли режим без хранения;
  - страна обработки;
  - эти три пункта вписать в политику конфиденциальности, в текст шита согласия в приложении и в Notes for Review для Apple.
- [ ] Где хранятся видео (CDN) и кто заливает новые эпизоды?
- [ ] Регионы: оставляем русские названия или переходим на ISO-коды (`RU`, `KZ`)?
- [ ] Локальные данные тестеров не переносим, при первом входе все начинают с 800. Подходит?
- [ ] **Где хостится прод и в какой юрисдикции.** Сейчас Fly.io (компания в США), регион `fra`: Франкфурт, Германия, ЕС. Для игроков из России это трансграничная передача персональных данных, а 152-ФЗ (ст. 18 ч. 5) требует записывать и хранить данные граждан РФ в базах на территории России. Решить: оставляем ЕС и принимаем риск, переносим базу в РФ или держим отдельный контур для российских игроков. От ответа зависят политика конфиденциальности и уведомление Роскомнадзора.
- [ ] **Как продавать PRO в России** (аудит, раздел 4, вопрос 1). Google Play приостановил оплату подписок в РФ, при российском счёте выплат падают платежи во всех странах. В App Store в РФ оплата только с баланса Apple Account. Решить: юрлицо и банк для выплат, в каких странах продаём PRO, нужна ли своя оплата для RU на Android (тогда это отдельная задача клиенту и серверу: свой вебхук и `isPro` из второго источника).
- [ ] **Ключи и секреты для прода:** ключ Sign in with Apple (`.p8`, Team ID, Key ID) для обмена кода и revoke; `REVENUECAT_SECRET_KEY` и `REVENUECAT_WEBHOOK_SECRET`; SMTP-ящик для писем удаления; `ADMIN_TOKEN`; Telegram-бот и чат модераторов. Без них соответствующие функции работают в режиме «пропустить и записать в журнал».
- [x] **Домен прода:** весь `amplua.app` смотрит на прод `amplua-api`. API и страницы политики, условий, удаления аккаунта и приглашений отдаёт один сервер.
- [x] **Вход ревьюера:** логин и пароль для одного служебного аккаунта (`POST /v1/auth/review`), включается на сервере. Скрытая дверь в клиенте: долгое нажатие на логотип.
